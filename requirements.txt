# Q-Knee dependencies, audited for Streamlit Community Cloud / Hugging
# Face Spaces (free-tier: <1GB RAM during container spin-up, and a build
# times out if pip has to resolve/download multi-GB wheels). The two
# levers that actually matter at that scale are below; everything else in
# this file is comparatively small (single-digit-to-low-double-digit MB).
#
#   1. CPU-only torch/torchvision wheels instead of PyPI's default CUDA
#      build. This is the dominant win: PyPI's default `torch` wheel
#      bundles the NVIDIA CUDA/cuDNN runtime and is 800MB-2GB+ depending
#      on version, which alone can blow both the RAM budget and the
#      build-time limit on a free-tier container that has no GPU to use
#      it with anyway. Routing is done via `pyproject.toml`'s
#      `[tool.uv.sources]` (scoped ONLY to `torch`/`torchvision`) rather
#      than a bare `--extra-index-url` line here — a top-level
#      `--extra-index-url` in requirements.txt applies to every package
#      `uv` resolves, not just these two, and was observed to cause `uv`
#      on Streamlit Community Cloud to consider download.pytorch.org's
#      index for unrelated packages (`requests`, `streamlit`) and pick an
#      incompatible candidate from it — a real deploy crash, not a
#      hypothetical. Scoping the extra index per-package in pyproject.toml
#      keeps the same ~150-200MB CPU-only wheels without that ambiguity.
#   2. `opencv-python-headless`, not `opencv-python` — ships without the
#      Qt/GTK GUI toolchain a headless server container never uses, which
#      is both a much smaller wheel and avoids missing-shared-library
#      install failures on a minimal Debian slim base image.
#   3. Upper bounds on torch/torchvision/numpy (and see `.python-version`
#      at the repo root, pinning the interpreter to 3.10.14): Render's
#      native Python buildpack defaults to the newest CPython (3.14 as of
#      this writing) when nothing pins it, and several packages here —
#      most notably `onnx`/`onnxruntime` (moved to requirements-dev.txt
#      below for exactly this reason) — have no prebuilt wheel for that
#      version yet, forcing a from-source CMake/Protobuf build that runs
#      the free-tier build container out of memory. Every version bound in
#      this file is chosen to have a universal `cp310-manylinux` wheel.
#
# PennyLane note: this project only ever simulates a 4-qubit circuit
# (`config.yaml`'s `quantum.n_qubits`), whose full state vector is 16
# complex amplitudes — trivial for PennyLane's default `default.qubit`
# (pure-Python/NumPy) simulator. The compiled `pennylane-lightning`
# backend exists for much larger qubit counts; pulling it in here would
# add a native-extension wheel for no simulation-speed benefit at n=4, so
# it's deliberately not listed.
